# openftgs-xr: VR/desktop player for openftgs models

You are the implementer of `openftgs-xr`, an Apache-2.0 Rust workspace that implements a player for openftgs models generated by `openftgs`, built twice from one codebase on Bevy and OpenXR: a Linux desktop player with keyboard and mouse, and a Meta Quest 3 OpenXR app with controllers, hand tracking and passthrough. The plan is the specification in `docs/spec/openftgs-xr-spec.md` with revisions documented in `docs/spec/README.md`; the owner is the person running this session.

**Languages** (owner rule, 2026-10-29). Rust for all application code; WGSL for shaders (WESL only where a Bevy shader import needs it); a minimal Kotlin or Java Android shim only where an Android API has no native path (the document picker, runtime permissions, camera access), kept to the few methods the spec's §2 lists; Python only in dev tooling (the skills' scripts, the fixture generation that drives openftgs); shell for build scripts. Nothing else without asking.

`docs/spec/openftgs-spec.md` is a copy of the openftgs spec ("FreeTimeGS — Clean-Room Specification & Architecture"), the spec of the package that writes the model files openftgs-xr loads. It is not this package's spec: it is the reference for those files, chiefly its §2.2 stable file interfaces (`ftgs-if`, `ftgs-checkpoint`, `ftgs-render-request` and `ftgs-renders`) and the conventions they carry. Cite its items with an `openftgs` prefix (`openftgs §2.2`, `openftgs D-65`, `openftgs Q-214`), so they never mix with openftgs-xr's own §n, D-n and Q-n. Never edit `docs/spec/openftgs-spec.md`: it changes only when the owner replaces it with a newer copy from openftgs.

## Guidelines rules (strict)

Allowed sources:
- Papers, the papers they cite, and general Gaussian-splatting literature.
- The openftgs repository, https://github.com/samaust/openftgs: the owner's package that writes the model files openftgs-xr loads. Its documentation and source code are allowed, read to understand how to read the files it generates (their layout, conventions and loaders). Read its license file first, as for any third-party project. Read it in the local clone at `$OPENFTGS_REPO`, which each developer sets to wherever they cloned it; if the variable is unset, ask the owner rather than searching the machine for a copy. Read its code and documentation in the clone; `gh` is for its issues ("Issues").
- The openftgs-synth dataset (owner rule, 2026-10-15; openftgs #108): the owner's rendered multi-view video dataset, CC0-1.0, local at `$OPENFTGS_DATASETS/synth`. Its data files, `DATASET_CARD.md`, `ASSETS.md` and `SHA256SUMS` are allowed. Its generator is GPL-3.0-or-later, so its source code is never read and its documentation follows the copyleft rule below.
- Third-party software, by its license (owner rule, 2026-10-11; the aim is that openftgs-xr can be published under Apache-2.0):
  - Under a permissive license that allows commercial use (MIT, BSD, Apache-2.0, ISC, PSF, zlib and the like): documentation and source code. Read the project's license file before its source code; where a project bundles code under other licenses, apply this rule to each part.
  - Under a copyleft license, strong or weak (GPL, AGPL, LGPL, MPL, EPL, CDDL and the like), a non-commercial license, or no license: documentation only, never source code. Examples: ffmpeg (LGPL or GPL), hypothesis and tqdm (MPL-2.0), Monado (BSL-1.0 main code, GPL parts in some distributions) and Meta's OpenXR SDK and samples (proprietary). Using them as dependencies, runtimes or programs, as §2 allows, is fine.
  - If you can't tell which side a license is on, ask before opening the source.
- Code copied or closely adapted from a permissive source keeps its attribution: a comment above the adapted code naming the project, file, commit or version and license; an entry in NOTICE where the license asks for one; and a source-log row. Vendored files keep their own license headers and license files.
- For software you may read only the documentation of, read the project's own documentation pages, never snippets from tools that index whole repositories: they can return source code (openftgs spec Appendix A).

Never allowed source, whatever the license:
- The source code of software under a copyleft, non-commercial or missing license.

If a search result, link, package or file looks like a never allowed source, don't open it. If you meet a forbidden source anyway: stop at once, take nothing from it, record it as an incident in `docs/prd/source-log.md`, and tell the owner before doing anything else.

Source log: every source you consult (a URL, a document, a third-party file or docstring you read) gets a row in `docs/prd/source-log.md` saying what it was and what you took from it. The spec's Appendix A is the spec's own source log; `source-log.md` continues it for the implementation. Reading this repository and the spec needs no row.

## Working from the openftgs-xr spec

- The spec is the source of truth.
- Ask approval before editing `docs/spec/openftgs-xr-spec.md` or its revision record `docs/spec/README.md` ("Editing the spec" in `docs/agents/guidelines.md`). `docs/spec/openftgs-spec.md` is never edited (above).
- Where the spec is silent, ambiguous or looks wrong, don't guess what another implementation might do:
  - If the choice changes no numbers, outputs or public API (private names, file layout inside a module), make it.
  - Otherwise make an explicit, provisional decision: add a row to `docs/prd/questions.md` (Q-n: spec location, gap, decision, rationale, alternatives, the test that would expose a wrong choice), mark the code with a `// Q-n` comment (`# Q-n` in TOML, YAML, shell and Python tooling), and tell the owner. Before a build (planning, grilling, triage), record the gap instead as a Q-n candidate on the tracker; the implement skills turn candidates into rows ("Where the prd files are written" in `docs/agents/guidelines.md`).
  - If the spec states something that seems wrong or contradicts itself, stop and ask before coding around it.
- The public API is the signatures in §2 plus the additions recorded as Q-n rows. The workspace's crates, their Rust paths and the binaries are named in §2. Where the spec names a crate, module, function or type but gives no signature, propose one as a provisional Q-n row, as for any gap; one row may cover all the new signatures of a module. Changing a signature §2 lists is not a gap: stop and ask. Each library crate's `lib.rs` re-exports (`pub use`) exactly its public API; every other item is `pub(crate)` or private, and a `pub` item with neither a §2 signature nor a Q-n row is a standards finding. Crates and modules depend only on the bands below them and, within a band, only on the crates and modules before them, in the order §2 gives, so dependencies run one way with no cycles. Dependencies, versions and licenses are in §2, pinned in the workspace's one `[workspace.dependencies]` table; add nothing outside them without asking.
- Build bottom-up, one milestone at a time, in the order of `docs/prd/milestones.md`. The file is empty until the openftgs-xr spec is written; its order will be a suggestion, not part of the spec. Each milestone runs as one PRD through the skills.
- Before writing a module, read the spec items in its §2 entry and everything they point to (sections, equations E-n, decisions D-n), plus the §3 tests that exercise them. At the start of each milestone, re-read §0 and the parts of §1–§3 it touches.
- A module is done when its §3 tests pass, with each test written from its description in the spec, not from the code.
- Every source file starts with an SPDX header: `// SPDX-License-Identifier: Apache-2.0` in Rust, WGSL, WESL, Kotlin and Gradle files, `# SPDX-License-Identifier: Apache-2.0` in TOML, YAML, shell and Python files. Vendored files keep their own license headers and license files.

The issue tracker at github.com/samaust/openftgs-xr is the owner's channel. Use `gh issue` to read and write there: every new Q-n row gets a decision issue labelled `q-n` and titled `Q-<n>: <short gap>`, opened once its number is final, and the answer goes back into `docs/prd/questions.md` (`docs/agents/issue-tracker.md`, "Q-n issues"). `gh` may also target github.com/samaust/openftgs, the openftgs tracker, but no other repository; create or change issues there only when the owner asks. A link in an issue is subject to the guidelines rules like any other link. Never delete or transfer issues.

## Commits

Small commits, one module or test group each. Each message cites the spec items it implements, by identifier (§n, E-n, D-n, U-n), and any Q-n it relies on. Work happens on a branch off `main`: an integration branch per PRD (or per issue implemented on its own), or a short branch for one small change (`spec-<slug>` for a spec edit the owner approved, `q-<n>-answer` for an answer to a Q-n row, `docs-<slug>` for glossary and module docs, `workflow-<slug>` for skills, agent docs and this file, `setup-skills-repair`). Every branch reaches `main` only by a `git merge --no-ff` that the owner has approved, never by a squash. A commit that implements no spec item says so (`Spec items: none`). Never push without asking: before pushing `main`, ask the owner "Push `main` to origin now?" and push only if they answer yes to that question, every time; an earlier approval doesn't cover a later push. Other branches stay local. Never commit datasets, build outputs (`target/`, APKs) or keystores.

Work on every branch in its own worktree, `.claude/worktrees/<branch>` (`git worktree add -b <branch> .claude/worktrees/<branch> main`), never in the main checkout: parallel sessions share it, so a branch switched there sends their commits to the wrong branch. Keep worktrees there, inside the repository. The main checkout stays on `main`, where merges into `main` are made. Run `cargo` inside the worktree, so it builds and tests that branch's code; `CARGO_TARGET_DIR` may point at a shared directory outside the repository to save disk and rebuilds. Once the branch is merged into `main` and the merge is checked (`git merge-base --is-ancestor <branch> main`), remove its worktree (`git worktree remove .claude/worktrees/<branch>`).
