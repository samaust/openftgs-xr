# The headless commands in `ftgsxr-app`

How `ftgsxr_app::headless` meets §1.7's command line and §2.1's signatures: the commands, their exit codes, the error they return, and the Q-n rows the module relies on. The spec items are §1.7 (command line), §1.15, §2.1 `ftgsxr_app::headless`, D-36 and U-33, U-34, R-15; this doc explains them and never overrides them. Begun in M-2 (#117) with the commands that need no GPU; `cmd_render` joined with #118 and `cmd_bench` with #122 (§3.5 B-1, B-3, B-5, B-6, §1.12 P-2 to P-4); B-9 joined in M-4 (#289, Q-155, Q-222), B-4 in M-8 (#733, Q-408, Q-430).

## The commands

| Command | Function | Success | Failure |
| --- | --- | --- | --- |
| `ftgsxr render MODEL REQUEST.json OUT.safetensors [--tier TIER]` | `cmd_render(model, request, out, tier, version)` | writes `OUT` as `ftgs-renders`, prints nothing, exit 0 | a request the model refuses or no GPU, exit 2; a non-finite render, exit 3; nothing written |
| none: the Quest's R-9 runner only (Q-414) | `cmd_render_stereo(model, request, out, tier, sort, version)` | as `render`, each left and right pair rendered together | as `render`; a request whose items do not pair, exit 2 (Q-426) |
| `ftgsxr info [--json]` | `cmd_info(version, json)` | prints the adapter reply, exit 0 | none |
| `ftgsxr validate MODEL ...` | `cmd_validate(models)` | one line of header information per model, exit 0 | the first invalid model, exit 2 |
| `ftgsxr import IF OUT` | `cmd_import(input, out)` | writes `OUT`, prints nothing, exit 0 | exit 2, nothing written |
| `ftgsxr export MODEL OUT` | `cmd_export(model, out)` | as `import` | as `import` |
| `ftgsxr bench NAME [--out BENCH.json] [--model MODEL]` | `cmd_bench(name, out, model)`; on the Quest `cmd_bench_on(name, out, model, headset)` (Q-406) | writes the benchmark file at `OUT` or prints it, exit 0; exit 3 when a budget regressed against the baseline | an unknown NAME, an invalid model, a malformed baseline or no GPU, exit 2 |

A usage error (a missing argument, an unknown subcommand) is clap's, and exits 2 too. The binary prints a failure as one line `ftgsxr: <code>: <user text>` on standard error and exits with `exit_code` (Q-77).

- **`render`.** The checks that need no GPU come first, so a wrong request is reported as such on any machine: the request is read (`read_request`, openftgs's checks), then the model (`open_model`, any §1.2 input), then the request's `time_unit` against the model's (E-REQ-UNIT) and its `sh_degree` against the model's L (E-REQ-DEGREE; null is L). Only then does the command open a `HeadlessRenderer` in the tier, which makes its own wgpu device without a Bevy `App` (§2.1 Builds), and load the model at the request's degree (Q-86). Each item renders at its timestamp from its camera, at the identity pose, over the request's background, rgb unclamped. The renders are kept in memory and the file is written once, after the last item, through `write_renders` (a temporary sibling renamed over `OUT`), so a failure on any item writes no file and leaves an older `OUT` as it was. The file's `producer` is `openftgs-xr <version> (<GPU adapter name>)` and its `request_sha256` the SHA-256 of the request file's bytes (Q-90). The tier defaults to `conformance`; `--tier` takes the five names of §1.12 and clap refuses any other.
- **`cmd_render_stereo`** (Q-414). R-9's device run renders two eyes at once, through `HeadlessRenderer::render_stereo`, which the Quest crate cannot name (§2.1's band table). The function makes `render`'s checks, then reads the items as left and right pairs, `<id>L` immediately followed by `<id>R` at one timestamp, as R-9's `R9_<P>` requests hold them (Q-415). Anything else (an odd count, ids that do not pair, a pair at two times) is refused before the GPU as E-FILE-VALUE with `items = <reason>`, exit 2, nothing written (Q-426). Each pair renders in the given sort mode; the file holds the renders in the request's order with `render`'s producer and `request_sha256`. `ftgsxr render` offers no option for it; the binary does not call it.
- **`info`.** The reply is built once (name, version, no query kinds, the rasterizer, openftgs's conventions with the transmittance stop null, D-7) and written two ways: with `--json` as `info_json`'s compact object, the form openftgs's harness reads; without it as one `key: value` line per field in the same order, the conventions flattened to `render_conventions.<key>` (Q-71), strings bare and other values as their JSON text (Q-77).
- **`MODEL` paths.** A checkpoint is given as its directory or as its `manifest.json`, which every command maps to the directory before the read, so the model, its errors and the file its identity hashes are the directory's (Q-260, the core's `checkpoint_dir`). The binary prints the path as given.
- **`validate`.** Each model is read in full and validated (`open_model`), not only its header, so every reader rule of §1.2 applies. The `ModelInfo` it returns comes from the loaded model; its size is that of the file the model's identity hashes, `params.safetensors` for a checkpoint (D-40, Q-76). The signature returns one `Result`, so when a model fails, the binary prints no line for the models before it.
- **`import` and `export`.** §1.7 gives the two commands one rule, so they share one private function. The input is validated first; then a `ftgs-if` input is copied byte for byte (the bytes copied are checked against the identity the validated read computed, so a file replaced between the two reads is refused), and a checkpoint or a PLY is written in its activated form through the core's `write_exchange`, which names the producer `openftgs-xr <version>` (Q-65, Q-72). Both writes go through a temporary sibling renamed over `OUT`, so a failed write leaves the old file, or none, and no temporary.

## `bench`: the benchmarks, their file and the baselines

`cmd_bench` (Q-67) is a thin command over six private benchmark functions in `headless/bench.rs`, one per desktop benchmark of §3.5, with B-4's in `headless/bench/b4.rs` and B-9's in `headless/bench/b9.rs`; NAME selects one, and the binary's clap accepts only those six (B-1, B-3, B-4, B-5, B-6, B-9). The setups (sizes, the camera orbit, frame counts, what a frame's time is) are Q-102's; the file and the comparison are Q-103's. The module's own helpers sit beside it: `headless/synthetic.rs` (the generator) and `headless/json.rs` (the file's writer and reader).

- **Order of the checks.** The name is checked first, then `--model` is read and validated (`open_model`, any §1.2 input), and only then does the command open the GPU, so a wrong argument is reported on any machine, as for `render`.
- **No headless renderer.** `HeadlessRenderer::render` reads every frame back and composites it on the CPU, and never writes the statistics block, so it can time neither a display frame nor the sort. The benchmarks drive the render layer's passes themselves on a `SplatDevice::headless()` device: `encode_prepare`, the splat draw into the 16-bit layer, the resolve onto an 8-bit sRGB target and `encode_stats`, each frame submitted and waited for. The descriptors come from Bevy's re-exports of wgpu (`bevy::render::render_resource`), so the app needs no wgpu dependency of its own (§2.1's band row lists bevy). The draw's pass is the bench's own (Q-87), and it passes `FrameBuffers::draw_timestamp_writes` as the pass's timestamp writes (Q-114), so the statistics block's `GpuTimes` time every pass. Two clocks result. The wall clock gives a frame's time, from encoding to the GPU's completion (Q-102): B-1's `fps_min`, `fps_mean` and `frame_ms_max`, and B-5's `load_s` and `s_per_100mb`. The GPU's timestamps give B-1's `gpu_cull_ms` (stages 1–3), `gpu_sort_ms` (stage 4), `gpu_draw_ms` (the splat draw) and `gpu_total_ms`, the first timestamp written to the last (Q-115), medians over the measured frames and reported, not budgeted (Q-81, Q-114), and B-3's `sort_ms`, the median `GpuTimes.sort`.
- **Synthetic models.** `synthetic_model` mirrors `ftgsxr_testkit::random_model` draw for draw, since the testkit is a dev-dependency only (§2.1); a private test checks the two agree. Its one addition, every row persistent, serves B-1 and B-3, whose frames would otherwise draw and sort only the rows active at the frame's τ, about a third of `random_model`'s at mid-span and fewer near the ends, where P-2's trained model has nearly every row active (Q-102). Their setups name these models `synthetic, every row persistent`; B-5 and B-6 keep `random_model`'s rows. The models are made one at a time and dropped after their setup, so a sweep holds one model on the GPU.
- **`--model`** replaces the synthetic sweep by the given model; the setups name it by its identity (D-40) instead of a synthetic label, so its figures never match a synthetic baseline's.
- **Validation.** The device's validation messages are taken after the run, so a debug build's `SplatDevice` doesn't panic on drop. They don't fail the command: each is logged, and one line in `notes`, `GPU validation reported <k> messages (Q-116): …`, gives them all, which the binary prints on standard error. R-16's guard sees only the Khronos layer's records, not these, so the bench `gpu_` tests fail when a report's notes, or the binary's standard error, hold that line (§1.13, Q-116).

### B-9: startup

B-9 (§3.5) times the desktop's startup in-process, from `App::new()` to the first frame drawn after the first `Uploaded` of a probe loaded through `AppPlugin`'s initial models, on an offscreen `SplatCamera`, once without and once with the UI; the figures are reported, not budgeted (Q-155). The probe is `--model` or a synthetic file written to a scratch directory, every row persistent; a frame counts as drawn when `SplatStats` first reports a splat, the frame being the update the statistics' delay puts it at, and never before the `Uploaded` (Q-222). The variant without the UI turns egui's primary context off; the variant with it checks that the context is on the camera. The Quest's half of B-9 is M-8's device benchmarks.

### B-4: the cull with and without the temporal index

B-4 (§3.5) reports the cull's GPU time and the rows it visits with the temporal index (E3) and with the cull dispatched over every row, and checks that the index is never slower (Q-408, Q-430). The sizes are N = 10⁵, 2.5 × 10⁵, 5 × 10⁵, 10⁶, 2 × 10⁶ and 3 × 10⁶, synthetic models of seed 1 at L = 0 with `random_model`'s rows, mostly transient, which is what the index exists for (`synthetic, random_model's rows`); `--model` replaces them by its one model. Each size is seen from Q-102's orbit camera 0 at the span's midpoint, in the run's tier with its own capacity C, through one frame buffer, 8 warm-up and 32 measured frames per setup as B-3's.

- **Without the index, with no switch.** The rows are packed once, in the index's order, and uploaded twice: setup `index: "temporal"` with the model's index, setup `index: "every row"` with the index of a single-timestamp model of N rows, every row persistent, whose dispatch range is 0..N at every τ. The cull still decides each row's activity by E3's test, so both setups draw the same splats (D-10), and `ftgsxr_render` gains no public switch (§2.4 rule 2: the index stays always on in the player).
- **Figures.** Per setup: `cull_ms`, the median `GpuTimes.cull` (stages 1–3: the cull and the one-workgroup size dispatch); `cull_ms_spread`, the largest minus the smallest of the 32; `rows_visited`, the dispatch range's rows at τ (`TemporalIndex::range`, the count the pass dispatches; N without the index); `visible_splats`; `overflow`, 1 when a measured frame overflowed C.
- **The check.** Two budgets per size, id `B-4`, on the `temporal` setup: `cull_ms` `at_most` the every-row median plus the tolerance, the larger of the run's spread (the larger of the two setups' `cull_ms_spread`) and 10 % of the every-row median, so a few hundredths of a millisecond of noise on a shared GPU, where the 32 frames' spread can be smaller than the gap, fail nothing (the owner's choice on #733), and `rows_visited` `at_most` N. A check not met is `pass: false` and a line on standard error, exit 0, as for any budget (Q-103). They compare with a stored `B-4.json` as any budget does; none is stored before #734's calibration.

### On the headset

`cmd_bench_on(name, out, model, headset)` (Q-406) is `bench` on a machine that may be the Quest; `cmd_bench` is its case without a headset. With `headset`, the headset's build fingerprint, it runs the benchmarks that need no XR session, B-3, B-4, B-5 and B-6 (any other NAME is `Input`), on the headless device before the session, as Dv-3 does (Q-122). The runs use `quest-balanced`, the Quest's default tier, with its 1.5 GiB budget, and every setup names the tier (Q-413); B-3's P-4 is the Quest's limit, 2.5 ms at C = 10⁶. The file's `machine` gains `headset` as its last member, the string as given; a field the device cannot give is `unknown`, as `driver` is without NVIDIA's file (Q-417). The stored baseline is `<NAME>.quest.json` (Q-406), which a headset run never shares with the desktop's. On Android the system's temporary directory is not the app's, so B-5's files go in `ftgsxr-bench-<pid>/` beside `out`, under `dv/` (Q-417).

A size the device refuses is kept in the sweep: one result per measure with `value` null and the reason in `skipped`, and no budget (Q-413, Q-417). B-3 checks its frame buffers' records, C times §1.12's record bytes (64 in `quest-balanced`'s shared-center mode), against the device's storage binding limit before it allocates, since `FrameBuffers::new` refuses nothing and a binding over the limit would be a validation error; on the Quest's 128 MiB binding that is C = 4 × 10⁶. A refused upload (E-MEM-BUDGET: the budget, or Q-377's binding rules) is a skipped size for B-3, B-4 and B-5 alike; B-4 checks its frame buffers' records of the tier's C the same way, and skips a size in both its setups. Both rules are the headset's: on the desktop a refused upload is still the run's E-MEM-BUDGET error (Q-117).

The Quest's runner and the `dv` lane's host tests are in `docs/modules/ftgsxr-quest/android.md`.

### The file

The format is Q-67's top level with Q-103's details: `format` `ftgsxr-bench`, `version` 1, `bench`, `machine` (`gpu`, `driver`, `os`, `cpu`, `threads`), `versions` (`ftgsxr`, `bevy`, `wgpu`), `profile` (`release` or `debug`: a debug build runs the validation layers, so only a release build's numbers are worth keeping), `results`, `budgets`, `baseline` (the file compared against, or null) and `notes`. A result is `{setup, measure, value, unit}` (a skipped size adds `skipped`, its `value` null, Q-417); a budget `{id, setup, measure, rule, limit, value, pass}`, its `rule` `at_least`, `at_most` or `within_1_percent`. Objects keep the writer's key order, two-space indented. The bevy and wgpu versions are constants beside the pin, which a test checks against `Cargo.lock`; no runtime API reports them. §2.1's row names no JSON crate for the app, so `json.rs` writes the file and reads a baseline back (the tests read the files with serde_json, a dev-dependency, as an independent reader).

### Baselines

A baseline is a stored benchmark file, `benchmarks/baselines/<NAME>.json` at the workspace root, committed after the owner's review of the first run on the reference machine (§3.5, Q-67); the path is the one the build saw, and the variable `FTGSXR_BENCH_BASELINES` names another directory (Q-103), which the regression test uses. Without a baseline nothing is compared, nor with one of another `profile` or `machine.gpu`: a debug run against a release baseline, or a run on another GPU, would list false regressions, so `baseline` is null and a line in the file's `notes` says which field differs (the library logs it and the binary prints it from the notes on standard error, Q-110's split), such as `baseline not compared: profile debug against release (Q-103)`. With a baseline of the run's profile and GPU, each budget of the run is matched with the baseline's budget of the same id, measure and setup (objects compared as sets of members, so a baseline rewritten by another tool still matches) and listed in `BenchReport.regressions` when it is more than 10 % worse in its rule's direction; the binary prints each on standard error and exits 3. Only budgets are compared, §3.5's "budgeted figure"; the other results are reported. A `within_1_percent` budget (B-6) is never compared: B-6 is deterministic and its own 1 % budget is the check. A budget not met is `pass: false` and a line on standard error, but exits 0 (Q-103). The baseline is read and parsed, and `--out`'s directory checked, before the GPU opens, so a malformed baseline (E-JSON) or a missing directory doesn't throw a run away (#194).

A baseline is a recorded timing: it is run alone on the machine, from a release build, with nothing else on the GPU. B-5's synthetic files are written just before they are read, so their reads come from the page cache; the file's notes say so (Q-102).

## `HeadlessError` and the exit codes

`Input` and `Environment` exit 2, `Numeric` exits 3 (§2.1, §1.15). §2.1's variants carry only a message, so the §1.15 code travels in the message's leading `E-…:` prefix (Q-64): `code()` reads it back, and `user_text()` is the rest. A message without a recognized prefix still has a code, E-FILE-FORMAT for `Input` and E-GPU-ADAPTER for `Environment` (Q-75). The commands turn every `CoreError` they meet, whether reading the input or writing the output, into `Input("<code>: <path>: <core user text>")`, so the line the user sees names the file that failed (Q-75).

`render` adds the render layer's errors (Q-90). E-REQ-DEGREE has no `CoreError`, so its message is composed with the prefix directly: `Input("E-REQ-DEGREE: <request>: Request degree X, model degree Y")`. A `RenderError` becomes `Environment("<code>: <user text>")` for the GPU conditions (no adapter, a lost device after its one recovery, a shader that fails, a model over what the loaded models leave of the memory budget, Q-74), all exit 2. A non-finite render becomes `Numeric("item <id>")`, exit 3, and a core error inside the render layer becomes Q-75's `Input` on the model's path.

## Dependencies

The module takes `ftgsxr-core` and, for `render`, `ftgsxr-render`'s `HeadlessRenderer` (§2.1's band table), which brings Bevy's render crates into the build; `bench` takes the render layer's passes and Bevy's re-exported wgpu descriptors (`bevy` with `bevy_render` and `bevy_color`, both in §2.1's row through bevy). The binary depends on `ftgsxr-app` and clap alone (§2.1). So it cannot name the core's `ModelKind`, and it tells a model's kind by its variant's name when printing `validate`'s lines. `ftgsxr_app` re-exports `QualityTier`, the type `cmd_render` takes, so the binary can turn `--tier`'s name into a tier with `QualityTier::by_name` (Q-89).
B-9 builds the app through `AppPlugin`, so `headless` comes after `plugin` in the crate's module order (Q-223, owner 2026-11-03).
